## 2. Схема данных

**Вторая база не создаётся.** Всё в общей `friedman.db`. `finance.db` в своё время
выделили не ради удобства, а потому что там ошибочная модель данных путала
«выставлено» и «получено» (`finance_core.py:1-33`). Здесь такой причины нет,
а связи с `leads`, `clients`, `projects` — прямые.

Пять новых таблиц. Все создаются лениво, по образцу `seller_messages`
(`bot.py:4540`), — существующий `init_db()` не трогается.

### `outreach_campaign` — ядро

```
id                INTEGER PK
company           TEXT NOT NULL
contact_name      TEXT
contact_role      TEXT
email             TEXT
email_source_url  TEXT          -- откуда взят адрес; без него SEND заблокирован
contact_basis     TEXT          -- основание контакта (§7 UWG), словами
website           TEXT
language          TEXT DEFAULT 'de'
status            TEXT DEFAULT 'new'
researched_at     TEXT
hypothesis        TEXT          -- JSON: 7 полей §5.2
offer             TEXT
subject           TEXT
final_body        TEXT
final_html        TEXT
sent_at           TEXT
gmail_message_id  TEXT
lead_id           INTEGER       -- связь с доской лидов (dashboard_biz.py:58)
client_key        TEXT          -- связь с clients (bot.py:175): «уже работали»
created_at, updated_at
```

### `outreach_fact` — факты с источниками

```
id, campaign_id, kind, fact TEXT, source_url TEXT NOT NULL, fetched_at
```

Отдельная таблица, а не JSON-поле, — ровно потому, что §5.1 требует «факт без
источника не попадает в письмо». Ограничение уровня строки исполняется само;
внутри JSON его пришлось бы проверять руками и оно бы протекло.

### `outreach_media` — изображения

```
id, campaign_id, role ('main'|'supporting'|'viz'), path, orig_name,
mime, bytes, width, height, sha256, purpose TEXT, approved INTEGER DEFAULT 0,
added_at
```

`purpose` — за что отвечает картинка, словами модели («эскиз для лобби»).
`approved` ставится только на шаге §5.4.

### `outreach_touch` — история касаний

```
id, campaign_id, seq, kind ('primary'|'followup'), subject, body,
sent_at, gmail_message_id, status, error
```

Первое письмо тоже сюда, `seq=1`, `kind='primary'` — иначе история контакта
разъезжается на две сущности.

### `outreach_event` — журнал

```
id, campaign_id, ts, actor ('owner'|'bot'|'system'), event, detail
```

Каждый переход состояния, каждый провал preflight, каждая ошибка API. Это же
источник для экспорта на макбук (§8).

### `outreach_suppression` — отказники

```
email TEXT PRIMARY KEY, reason, added_at
```

Проверяется в preflight. Требование §15 спеки «уважать отказ».

**Что переиспользуется, а не дублируется:** `settings` (флаги, реквизиты
отправителя, DRY_RUN), `clients` (`bot.py:175`) для матчинга «уже работали»,
`leads` (`dashboard_biz.py:58`) — выигранная кампания может породить лид,
`get_funnel_context()` / `get_legal_context()` — контекст в промпты.

**Миграции.** Схема применяется функцией `_ensure_tables(conn)`, идемпотентно,
при каждом входе в модуль. Версия схемы — в `settings['outreach_schema_v']`;
добавление колонки в будущем идёт через `ALTER TABLE` под проверкой версии.

## 3. Машина состояний

```
        ┌──────────────────────────── owner: /outreach <ссылка|название>
        ▼
      NEW ──► RESEARCH ──► STRATEGY ──► MATERIALS ──► DRAFT ──► APPROVAL
                                                                   │
                                          owner: «отправляй» ──────┤
                                                                   ▼
                                        preflight OK ──►  READY ──► SENT
                                                                   │
                                                                   ▼
                                                              FOLLOWUP
        любое состояние ──► BLOCKED (причина) ──► возврат назад
        любое состояние ──► ABANDONED (owner отказался)
```

Правила, которые делают это надёжным:

1. **Состояние живёт в БД, не в `ctx.user_data`.** В проекте рестарты штатные —
   `/restart` через `os.execv` (`sales_bot.py:117`), супервизия `_restart_sales`
   (`bot.py:5515`), `/update`. Существующий `pending_plan` (`bot.py:3581`) память
   процесса и переживает не всё; кампания, собиравшаяся полчаса, так теряться
   не должна. В `ctx.user_data` лежит только `active_campaign_id`, и он же
   продублирован в `settings['outreach_active']`.
2. **Статус меняет ровно одна функция** — `advance(cid, to, actor, note)`. Она же
   пишет в `outreach_event`. Никакой другой код не делает `UPDATE ... status`.
   Разрешённые переходы — таблицей, попытка прыгнуть через шаг падает с ошибкой.
3. **Назад можно, вперёд по-тихому нельзя.** «Перепиши письмо» возвращает
   DRAFT→DRAFT, «замени картинку» — DRAFT→MATERIALS. Возврат сбрасывает
   `approved` у медиа и обнуляет `final_body`, чтобы не отправить старую версию.
4. **APPROVAL истекает.** Утверждение старше 24 часов не считается: если между
   «подтверждаю» и отправкой прошли сутки, показываем письмо заново. Защита от
   «ой, я вчера что-то там подтвердил».
5. **Одна тяжёлая цепочка за раз** — `_outreach_lock`, как `_orch_lock` у Директора
   (`director_bot.py:282`). RESEARCH занимает минуты; вторая параллельная забьёт
   квоту и перемешает ответы.

## 4. Промпты и база знаний

Три отдельных вызова Claude CLI вместо одного большого — каждый со своей моделью,
своим набором инструментов и своим таймаутом. Механика ровно та же, что у
`sales_dialog_sync()` (`bot.py:4571`): `_claude_exec`, роль через
`--append-system-prompt`, `SKILL.md` инлайнится через `_kb_inline` (`bot.py:666`),
`references/*.md` модель читает сама.

| Шаг | Функция | Модель / инструменты | Выход |
|---|---|---|---|
| RESEARCH | `research_sync(seed)` | sonnet, `WebSearch,WebFetch,Read`, `--max-turns 14`, timeout 600 | JSON: `facts[{fact, source_url, kind}]`, `contact{name, role, email, email_source_url, basis}`, `gaps[]` |
| STRATEGY | `strategy_sync(cid)` | sonnet, `Read`, `--max-turns 8`, timeout 300 | JSON: 7 полей гипотезы §5.2 + `needed_images[{role, description}]` |
| DRAFT | `draft_sync(cid)` | sonnet, `Read`, `--max-turns 8`, timeout 300 | JSON: `subject`, `body`, `used_fact_ids[]` |

`used_fact_ids` — не украшение. Это то, что preflight сверяет с `outreach_fact`:
письмо не может опираться на факт, которого нет в базе с источником.

**Жёсткие требования в промптах** (в KB, не в коде):
- факт без URL не выдавать вообще, а перечислять в `gaps`;
- «данных мало» — валидный ответ, домысел — нет;
- маркетинговые термины из `references/strategy.md` — инструмент мышления,
  в текст письма не попадают (§5.2 спеки);
- отраслевых веток нет: разница между отелем и архбюро рождается из фактов
  исследования, шаблонов по типам клиентов в KB не существует (§2 спеки).

**Контекст, который подмешивается:** `get_legal_context()`, `get_funnel_context()`,
факты кампании, гипотеза, профиль художника. Профиль (22 года практики,
FSV Frankfurt, Cansativa, Montana Colors, Caparol, услуги) кладётся в
`outreach_kb/references/artist.md` — один источник правды, не разбросан по промптам.

**Самолечение** — `ensure_outreach_kb()` по образцу `ensure_sales_kb()`
(`bot.py:2109`), плюс все файлы в `UPDATE_FILES` (`bot.py:5257`), иначе на сервер
они не доедут.

## 5. Изображения

**Хранение:** `friedman_bot/outreach_media/<campaign_id>/<uuid>.<ext>` на сервере,
каталог в `.gitignore`. Прецедент постоянного каталога — `invoices_pdf/`
(`bot.py:21`). В БД лежит путь, не блоб: SQLite с шестью писателями не место
для мегабайтов.

**Приём:** в `sales_bot.py` добавляются `filters.PHOTO` и `filters.Document.IMAGE`.
Сейчас фото принимает только Секретарь (`bot.py:6933`) и сразу удаляет файл
(`bot.py:3658`) — здесь наоборот, файл остаётся.

**Назначение роли определяет бот, не имя файла** (§5.3). После загрузки модель
смотрит на файл через `Read` — механика уже отлажена в `_analyze_as_wall`
(`bot.py:3505`) — и отвечает: что изображено, какой из `needed_images` закрывает,
годится ли для этого клиента. Владелец не пишет технических имён.

**Оптимизация** (Pillow уже в зависимостях): длинная сторона ≤ 2000 px, JPEG q=85,
цель ≤ 1.5 МБ на файл и ≤ 6 МБ на письмо. Лимит Gmail API — 25 МБ, но тяжёлое
письмо хуже доходит; 6 МБ — запас по доставляемости, а не по API. EXIF срезается
(в нём бывает геолокация — это чужая стена и наш адрес). Оригинал сохраняется
рядом, в письмо идёт оптимизированная копия.

**Отбор** (§5.4): бот предлагает состав — 1 main, 1–4 supporting, опционально viz —
с обоснованием по каждой. Кнопки: подтвердить / убрать N / добавить ещё.
`approved=1` проставляется только после явного «да» и слетает при возврате в
MATERIALS.

## 6. Gmail

**Scope: только `gmail.send`.** Обоснование: модулю нужно ровно одно — отправить.
`gmail.compose` дал бы право создавать и читать черновики; черновики нам не нужны,
роль «покажи перед отправкой» выполняет DRY_RUN, который пишет `.eml` на диск.
Каждый лишний scope — это лишний экран разрешений и лишний риск. `gmail.send`
относится к sensitive-скоупам (не restricted): аудита безопасности не требует.

**Файлы (оба в `.gitignore`):**
- `friedman_bot/.gmail_client.json` — client_id/secret из Google Cloud Console
- `friedman_bot/.gmail_token.json` — refresh-токен

Пароль Gmail не хранится нигде и не используется — только OAuth.

**Первичная авторизация на headless-сервере.** Браузера там нет, поэтому:
1. на макбуке запускается `python3 gmail_send.py --authorize` → открывается браузер → выдаётся доступ;
2. появившийся `.gmail_token.json` копируется на сервер через `scp`;
3. дальше сервер обновляет токен сам, браузер больше не нужен.

Никакой эмуляции кликов в веб-Gmail (запрет §2 спеки) — только официальный API.

**Развилка аккаунта.** Модуль работает одинаково в обоих случаях, разница —
в эксплуатации:

| | Обычный Gmail | Workspace на farbaholix.de |
|---|---|---|
| Тип приложения | External | **Internal** |
| Верификация | нужна для Production, иначе статус Testing | не нужна |
| Refresh-токен в Testing | **отзывается каждые 7 дней** | не применяется |
| Адрес отправителя | `...@gmail.com` | `viacheslav@farbaholix.de` |

Рекомендация — Workspace. Семидневка на сервере означает еженедельную ручную
переавторизацию, а адрес на своём домене для архбюро и отельных групп —
часть продукта. Если остаётся обычный Gmail, единственный рабочий путь —
перевести приложение в Production и пройти верификацию.

**Сборка письма:** `EmailMessage` из стандартной библиотеки, `multipart/alternative`
(text + HTML), вложения с реальным MIME по сигнатуре файла, кодирование
base64url, отправка `users.messages.send`. Ответ содержит `id` — он и пишется в
`gmail_message_id`.

**Ошибки API:** кампания **не** помечается отправленной при неудаче. Статус
остаётся READY, ошибка ложится в `outreach_event` и приходит владельцу словами
(«Gmail отказал: токен истёк — нужна переавторизация»), а не трейсбеком.
Повтор — отдельным подтверждением.

## 7. DRY_RUN и предполётная проверка

**DRY_RUN включён по умолчанию.** Флаг: env `OUTREACH_DRY_RUN` →
`settings['outreach_dry_run']`, значение по умолчанию `true`. Выключается только
явной командой владельца, и бот при этом переспрашивает.

В режиме DRY_RUN проходит **весь** путь, включая preflight и сборку MIME. Готовое
письмо сохраняется как `outreach_out/<cid>-<ts>.eml` и присылается в Telegram
документом — файл открывается в Mail и выглядит ровно так, как его увидит
получатель. Строка отправки — единственное, что не выполняется.

**Preflight — чистая функция** `preflight(cid) -> list[Problem]`, каждая проверка
отдельно и тестируема. Любой `BLOCK` останавливает отправку и показывается
владельцу причиной.

| Проверка | Уровень |
|---|---|
| e-mail синтаксически валиден, домен согласуется с `website` | BLOCK |
| `email_source_url` и `contact_basis` заполнены | BLOCK |
| адреса нет в `outreach_suppression` | BLOCK |
| нет SENT-кампании с этим e-mail и `kind='primary'` (§7 спеки) | BLOCK |
| каждый `used_fact_id` существует в `outreach_fact` и имеет `source_url` | BLOCK |
| в теле нет плейсхолдеров и следов разметки (`[`, `{`, `TODO`, `XXX`, `Ihr Name`) | BLOCK |
| вложения = утверждённому набору; файлы на месте; MIME по сигнатуре; размер в лимите | BLOCK |
| в теле не встречаются `company` / `contact_name` **других** кампаний | BLOCK |
| в теле нет внутренних терминов (гипотеза, «сегмент», «pain point», «ICP») | BLOCK |
| отправительский блок присутствует | BLOCK |
| строка отказа от дальнейших писем присутствует | BLOCK |
| Gmail API отвечает, токен жив (проверка без отправки) | BLOCK |
| почтовый адрес в отправительском блоке отсутствует | **WARN** (см. §9) |
| письмо длиннее 250 слов — «это уже портфолио-дамп» | WARN |

## 8. Экран утверждения и UX

Формат карточки — как в §5.6 спеки, дословно: получатель, e-mail, subject,
attachments, полный текст. Плюс блок «на чём построено» — факты со ссылками,
чтобы было видно, откуда взялось каждое утверждение.

Подтверждение — **кнопкой** `[Отправить]` (`CallbackQueryHandler`, механика
`bot.py:3665`), не текстом. «Ок», «наверное», молчание и уход в другую тему
подтверждением не считаются (§5.6). Кнопка живёт 24 часа, дальше показ заново.

Команды бота:

```
/outreach <ссылка|название>   новая кампания → RESEARCH
/campaigns                    список: компания · статус · дата
/campaign <id>                карточка: что отправляли, когда, чем ответили
/followup <id>                подготовить следующее касание
/outreach_stop <email>        занести в отказники
/outreach_export <id>         ZIP: campaign.json + факты + письмо + медиа + журнал
/dryrun [on|off]              режим (по умолчанию on)
```

**`/outreach_export` — это ответ на «продолжить с макбука».** ZIP содержит, помимо
машинных данных, файл `state.md` — человекочитаемый пересказ кампании и журнала
событий. Его можно отдать Claude на макбуке, и тот подхватит работу, не имея
доступа к серверной базе. Механика ZIP уже есть в проекте (`bot.py:6515`).

## 9. Правовой контур (§15 спеки)

Реализуется как архитектура, а не опция:

- **Источник адреса** — `email_source_url` обязателен, без него preflight блокирует.
  Правило в KB: адрес принимается, только если найден на публичной странице
  компании (Impressum / Kontakt / страница команды).
- **Основание контакта** — `contact_basis` словами: кто адресат, почему именно он
  и почему предложение относится к его работе.
- **Отправительский блок** — из `settings`: `outreach_sender_name` (Viacheslav
  Balabaiev), `outreach_sender_site` (farbaholix.de), `outreach_sender_phone`
  (+49 151 724 50347), `outreach_sender_address` (пока пусто).
- **Отказ** — в каждом письме строка на немецком: ответьте «kein Interesse», и я
  больше не пишу. Ответ → `/outreach_stop` → `outreach_suppression` → preflight
  блокирует навсегда.
- **Журнал** — `outreach_event` хранит, что и на каком основании отправлено.

## 10. План реализации по этапам

Каждый этап — отдельный коммит и отдельный проверяемый результат. Следующий не
начинается, пока предыдущий не проверен.

| # | Этап | Как проверяется |
|---|---|---|
| 1 | Схема БД, FSM, CRUD, `/outreach`, `/campaigns`, `/campaign` — без ИИ и без почты | Создать фиктивную кампанию, увидеть её в списке, пройти переходы руками; `py_compile` чист |
| 2 | RESEARCH + STRATEGY, `outreach_kb/` | На фиктивном клиенте: факты приходят с URL, при нехватке данных бот говорит «мало», гипотеза заполнена |
| 3 | MATERIALS: приём фото, хранение, оптимизация, роли, отбор и подтверждение | Загрузить 3 картинки, получить предложение состава с обоснованием, подтвердить, увидеть `approved=1` |
| 4 | DRAFT + APPROVAL: генерация, карточка, кнопки, возвраты назад | Письмо на немецком, кнопка «изменить текст» возвращает в DRAFT, `approved` слетает |
| 5 | MIME + preflight + DRY_RUN | `.eml` приходит в Telegram, открывается в Mail; каждая проверка preflight ломается искусственно и блокирует |
| 6 | `gmail_send.py`, OAuth, SEND, LOG, блокировка повторной первичной отправки | Реальная отправка на свой же адрес; вторая попытка тому же контакту блокируется |
| 7 | FOLLOWUP, suppression, `/outreach_export` | Follow-up требует подтверждения; `/outreach_stop` блокирует; ZIP открывается и читается |
| 8 | `UPDATE_FILES`, `ensure_outreach_kb`, `.gitignore`, `SETUP-GMAIL.md` | `/update` на сервере поднимает модуль с нуля |

Регресс на каждом этапе: `python3 -m py_compile` на все тронутые файлы, запуск
`sales_bot.py` с проверкой, что `/sales`, `/funnel`, `/digest`, голос и утренний
дайджест работают как раньше.

## 11. Риски — честно

1. **Gmail и семидневка.** Главный эксплуатационный риск. На обычном Gmail в статусе
   Testing бот будет отваливаться раз в неделю, и выяснится это в худший момент —
   когда письмо готово. Лечится только выбором из §6, не кодом.
2. **Галлюцинация с источником.** Требование «факт + URL» отсекает выдумку без
   ссылки, но не отсекает случай, когда модель приписала реальному URL то, чего там
   нет. Смягчаю показом фактов со ссылками на экране утверждения — но полностью
   это не решается, и последняя проверка остаётся на тебе. Обещать иное было бы
   враньём.
3. **Право.** UWG §7 для холодных B2B-писем узок: «предполагаемое согласие» —
   исключение, а не правило. Модуль умеет фиксировать основание и уважать отказ,
   но законной практику делает не он.
4. **Долгие вызовы.** RESEARCH до 10 минут. `_outreach_lock` не даст цепочкам
   наложиться, но пока идёт исследование, бот на другие тяжёлые запросы отвечает
   «в очереди». Быстрые команды (`/funnel`) не блокируются.
5. **SQLite и шесть писателей.** Транзакции короткие, длинные операции идут вне БД,
   результат пишется одним движением. Иначе `database is locked` — известная в
   проекте боль (`bot.py:75-78`).
6. **Квота Claude.** Аутрич и утренний дайджест конкурируют за одну подписку.
   Совпадут по времени — что-то вернёт пустоту. Смягчение: RESEARCH не запускается
   автоматически по расписанию, только руками.
7. **Рост медиа на диске.** Каталог не чистится сам. Нужен ретеншен (кампании
   старше N месяцев — архив) — предлагаю отложить до этапа 7 и решить по факту.
8. **Приём фото в «Маркетологе».** Добавление `filters.PHOTO` меняет поведение бота:
   раньше фото он игнорировал. Вне активной кампании он должен вежливо отвечать
   «сейчас не собираю материалы», а не молчать и не пытаться что-то анализировать.
